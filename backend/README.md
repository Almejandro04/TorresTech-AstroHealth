# AstroHealth backend

FastAPI service for the AstroHealth MVP. Response shapes follow
[`docs/api_contract.md`](../docs/api_contract.md) v0.1.0.

## English

### Current scope

- BACKEND-01 (#3): service initialization and `GET /api/health`.
- BACKEND-02 (#7): contract models (`app/models/`) and SQLite storage
  (`app/database/`) with seed and reset commands.

Not implemented yet: astronaut/readings/journal/summary/alerts endpoints and the
HTTP error envelope (#8), CSV import and replay (#9), baselines and analysis
(#14), alert rules (#15), and authentication. The API does not open the
database yet; only the commands below and the tests use it.

### Requirements

- Python 3.13 (verified with 3.13.3 on Windows 11). The pinned dependencies
  require Python 3.11 or newer; other versions have not been verified.
- Runtime dependencies are pinned in `requirements.txt`; test dependencies in
  `requirements-dev.txt`, which includes the runtime file.

### Setup (PowerShell, from the repository root)

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend\requirements-dev.txt
```

The commands below call the virtual environment's interpreter by path, so
activating it is optional. On macOS/Linux use `.venv/bin/python` instead.

### Run (from the `backend` folder)

```powershell
cd backend
..\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000
```

| What | URL |
| --- | --- |
| Health | <http://localhost:8000/api/health> |
| Swagger UI | <http://localhost:8000/docs> |
| OpenAPI | <http://localhost:8000/openapi.json> |

The frontend uses `VITE_API_BASE_URL=http://localhost:8000`. Uvicorn listens on
`127.0.0.1` (IPv4). On Windows, command-line clients that try IPv6 first can
take about 2 seconds to connect through `localhost`; `http://127.0.0.1:8000`
avoids that delay.

### CORS

Allowed origins come from the `ASTROHEALTH_CORS_ORIGINS` environment variable:
a comma-separated list of exact origins. When it is unset or blank, the only
allowed origin is `http://localhost:5173`. The wildcard `*` is rejected at
startup.

```powershell
$env:ASTROHEALTH_CORS_ORIGINS = "http://localhost:5173,http://127.0.0.1:5173"
```

### Checks (from the `backend` folder)

```powershell
..\.venv\Scripts\python.exe -m pytest
..\.venv\Scripts\python.exe -m pip check
```

Warnings are treated as test failures (`pytest.ini`). Tests create their
databases in temporary folders and never touch the configured one.

### Database (from the `backend` folder)

The database is one local SQLite file. `ASTROHEALTH_DB_PATH` selects it; when
it is unset or blank the file is `backend/astrohealth.db`. A relative value is
resolved against the current folder. Database files are git-ignored; do not
commit them.

```powershell
..\.venv\Scripts\python.exe -m app.database init
..\.venv\Scripts\python.exe -m app.database seed
..\.venv\Scripts\python.exe -m app.database reset
```

| Command | Effect |
| --- | --- |
| `init` | Creates the tables if they are missing. Existing data is kept. |
| `seed` | Runs `init`, then loads `docs/examples/mission_seed.json`: one source, two fictional astronauts, and seven days of readings and journal entries for `AST-001`. It is all-or-nothing and can be repeated; note that it rewrites the seeded journal days with the seed values. |
| `reset` | Deletes the database file (and its `-journal`, `-wal`, `-shm` files), then runs `init` and `seed`. The result is always the same rows and IDs. It refuses to delete a file that is not a SQLite database. Stop the API first: Windows cannot delete an open file. |

To use another file for one session:

```powershell
$env:ASTROHEALTH_DB_PATH = "C:\temp\astrohealth-demo.db"
```

### Stored records and uniqueness

Tables: `sources` (manifest), `astronauts`, `readings`, `journal`, `alerts`.
Every reading, journal entry, and alert keeps its astronaut, UTC timestamp,
mission day, `source_type`, and `source_id`; readings also keep
`measurement_context`. IDs are generated by the backend (`READING-0001`,
`JOURNAL-0001`, `ALERT-0001`) and are never reused.

| Record | Unique key | Writing the same key again |
| --- | --- | --- |
| Reading | astronaut, timestamp, `measurement_context` | Identical values: the stored reading is returned, nothing is written. Different values or provenance: conflict, nothing is written. |
| Journal | astronaut, `mission_day` | The entry is replaced and keeps its `journal_id`. An entry cannot move to another day. |
| Alert | astronaut, `rule_id`, `rule_version`, `indicator`, timestamp | The alert is updated and keeps its `alert_id`; this is how it becomes resolved. |

Timestamps must be UTC and end in `Z`, with seconds and up to six fractional
digits. Equivalent forms such as `12:00:00Z` and `12:00:00.000Z` are the same
key. A missing value is stored as `NULL` and read back as `null`; it is never
replaced by `0` or by an earlier value.

### Schema validity is not clinical normality

Validation checks shape only: types, units, scales (for example SpO2 0-100,
mood 1-5, sleep 0-24 hours), required fields, the mission day matching the
timestamp, and known astronaut and source references. A heart rate of 250 is
stored like any other value. Deciding whether a value deserves attention
belongs to the analysis and alert issues (#14, #15).

### How the journal will join the summary (#8)

Journal entries and vital readings are separate tables with different cadence.
In `latest_metrics`, `sleep_hours_last_night` and `mood_score` will come from
the journal, and the three vital metrics from readings. Each metric is chosen
independently as its latest non-null value, and keeps its own timestamp,
mission day, provenance, and record ID. This issue only stores the data needed
for that; the summary itself is not implemented.

### Registros almacenados y unicidad

Tablas: `sources` (manifiesto), `astronauts`, `readings`, `journal`, `alerts`.
Cada lectura, entrada de diario y alerta conserva su astronauta, timestamp UTC,
día de misión, `source_type` y `source_id`; las lecturas conservan además
`measurement_context`. Los IDs los genera el backend (`READING-0001`,
`JOURNAL-0001`, `ALERT-0001`) y nunca se reutilizan.

| Registro | Clave única | Al escribir de nuevo la misma clave |
| --- | --- | --- |
| Lectura | astronauta, timestamp, `measurement_context` | Valores idénticos: se devuelve la lectura guardada y no se escribe nada. Valores o procedencia distintos: conflicto, no se escribe nada. |
| Diario | astronauta, `mission_day` | La entrada se reemplaza y conserva su `journal_id`. Una entrada no puede moverse a otro día. |
| Alerta | astronauta, `rule_id`, `rule_version`, `indicator`, timestamp | La alerta se actualiza y conserva su `alert_id`; así pasa a resuelta. |

Los timestamps deben ser UTC y terminar en `Z`, con segundos y hasta seis
dígitos de fracción. Formas equivalentes como `12:00:00Z` y `12:00:00.000Z` son
la misma clave. Un valor ausente se guarda como `NULL` y se lee como `null`;
nunca se sustituye por `0` ni por un valor anterior.

### Validez de esquema no es normalidad clínica

La validación comprueba solo la forma: tipos, unidades, escalas (por ejemplo
SpO2 0-100, ánimo 1-5, sueño 0-24 horas), campos requeridos, que el día de
misión coincida con el timestamp y que el astronauta y la fuente existan. Una
frecuencia cardíaca de 250 se guarda como cualquier otro valor. Decidir si un
valor merece atención corresponde a los issues de análisis y alertas (#14, #15).

### Cómo se unirá el diario al summary (#8)

Las entradas de diario y las lecturas vitales son tablas separadas con cadencia
distinta. En `latest_metrics`, `sleep_hours_last_night` y `mood_score` vendrán
del diario, y las tres métricas vitales de las lecturas. Cada métrica se elige
de forma independiente como su último valor no nulo y conserva su propio
timestamp, día de misión, procedencia e ID de registro. Este issue solo guarda
los datos necesarios para ello; el summary no está implementado.
