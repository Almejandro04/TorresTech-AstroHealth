- BACKEND-02 (#7): contract models (`app/models/`) and SQLite storage

### Database (from the `backend` folder)

The database is one local SQLite file. `ASTROHEALTH_DB_PATH` selects it; when
it is unset or blank the file is `backend/astrohealth.db`. A relative value is
resolved against the current folder. Database files are git-ignored; do not
commit them.

```powershell
..\.venv\Scripts\python.exe -m app.database init
..\.venv\Scripts\python.exe -m app.database seed
..\.venv\Scripts\python.exe -m app.database reset
```

| Command | Effect |
| --- | --- |
| `init` | Creates the tables if they are missing. Existing data is kept. |
| `seed` | Runs `init`, then loads `docs/examples/mission_seed.json`: one source, two fictional astronauts, and seven days of readings and journal entries for `AST-001`. It is all-or-nothing and can be repeated; note that it rewrites the seeded journal days with the seed values. |
| `reset` | Prepares and validates a seeded temporary database before replacing an identified AstroHealth database. Refuses unknown/foreign files, ambiguous paths, links and any `-journal`/`-wal`/`-shm` sidecars. Never deletes sidecars. Stop all database clients and let SQLite close/checkpoint normally first. Preparation failure preserves the previous database. |

To use another file for one session:

```powershell
$env:ASTROHEALTH_DB_PATH = "C:\temp\astrohealth-demo.db"
```

### Stored records and uniqueness

Tables: `sources` (manifest), `astronauts`, `readings`, `journal`, `alerts`.
Every reading, journal entry, and alert keeps its astronaut, UTC timestamp,
mission day, `source_type`, and `source_id`; readings also keep
`measurement_context`. IDs are generated by the backend (`READING-0001`,
`JOURNAL-0001`, `ALERT-0001`) and are never reused.

| Record | Unique key | Writing the same key again |
| --- | --- | --- |
| Reading | astronaut, timestamp, `measurement_context` | Identical values: the stored reading is returned, nothing is written. Different values or provenance: conflict, nothing is written. |
| Journal | astronaut, `mission_day` | The entry is replaced and keeps its `journal_id`. An entry cannot move to another day. |
| Alert | astronaut, `rule_id`, `rule_version`, `indicator`, timestamp | The alert is updated and keeps its `alert_id`; this is how it becomes resolved. |

Timestamps must be UTC and end in `Z`, with seconds and optional fractional
digits of arbitrary length, preserved without rounding. Equivalent forms such as `12:00:00Z` and `12:00:00.000Z` are the same
key. A missing value is stored as `NULL` and read back as `null`; it is never
replaced by `0` or by an earlier value.

### Schema validity is not clinical normality

Validation checks shape only: types, units, scales (for example SpO2 0-100,
mood 1-5, sleep 0-24 hours), required fields, the mission day matching the
timestamp, and known astronaut and source references. A heart rate of 250 is
stored like any other value. Deciding whether a value deserves attention
belongs to the analysis and alert issues (#14, #15).

### How the journal joins the summary (#8)

Journal entries and vital readings are separate tables with different cadence.
In `latest_metrics`, `sleep_hours_last_night` and `mood_score` come from
the journal, and the three vital metrics from readings. Each metric is chosen
independently as its latest non-null value, and keeps its own timestamp,
mission day, provenance, and record ID. Raw histories retain nulls and gaps.

### REST API and demo

| Method | Route | Success |
| --- | --- | --- |
| GET | `/api/health` | 200 |
| GET | `/api/astronauts` | 200, paginated profiles |
| GET / POST | `/api/astronauts/{id}/readings` | 200 list/retry; 201 create |
| GET / POST | `/api/astronauts/{id}/journal` | 200 list/correction/retry; 201 create |
| GET | `/api/astronauts/{id}/summary` | 200, independent snapshots |
| GET | `/api/astronauts/{id}/alerts` | 200, empty unevaluated collection |

Lists accept `limit` (1–1000, default 100) and `offset` (>=0, default 0).
Histories/alerts also accept inclusive `from_day`/`to_day` inside the mission.
Reversed bounds are invalid. Histories, summary and alerts accept `as_of`:
UTC ending in Z, within the mission. Without it the latest persisted reading
or journal timestamp is used, or null for an empty profile. Records after that
cutoff are excluded; each snapshot retains its own original time and ID.
Profiles sort by ID; readings/journal by timestamp then generated ID ascending.
Alerts additionally accept `status=active|resolved`. List totals are counted
after filtering and before pagination. Errors never mean an empty history.

All successes use `data/meta`; all errors use `error/meta`, with
`error.code`, `message` and `details[{field,message}]`. Codes: 404
`ASTRONAUT_NOT_FOUND` for missing profiles, 404 `NOT_FOUND` for unknown routes,
405 `METHOD_NOT_ALLOWED`, 409 `READING_CONFLICT`, 422 `VALIDATION_ERROR`
(fields prefixed `body.*`/`query.*`), and generic 500 `INTERNAL_ERROR`.
Health/profiles use `meta.as_of=null`. POST responses use the effective latest
observation cutoff, so their data passes the frontend's `matchesView` guard.

Baselines use `not_implemented`, null values/context/method/windows and zero
samples until #14. Alerts use `not_implemented`, `data=[]`, `total=0`;
summary active count/severity are null and recent alerts empty until #15.
An empty unevaluated alert list is not an all-clear.

### Registros almacenados y unicidad

Tablas: `sources` (manifiesto), `astronauts`, `readings`, `journal`, `alerts`.
Cada lectura, entrada de diario y alerta conserva su astronauta, timestamp UTC,
día de misión, `source_type` y `source_id`; las lecturas conservan además
`measurement_context`. Los IDs los genera el backend (`READING-0001`,
`JOURNAL-0001`, `ALERT-0001`) y nunca se reutilizan.

| Registro | Clave única | Al escribir de nuevo la misma clave |
| --- | --- | --- |
| Lectura | astronauta, timestamp, `measurement_context` | Valores idénticos: se devuelve la lectura guardada y no se escribe nada. Valores o procedencia distintos: conflicto, no se escribe nada. |
| Diario | astronauta, `mission_day` | La entrada se reemplaza y conserva su `journal_id`. Una entrada no puede moverse a otro día. |
| Alerta | astronauta, `rule_id`, `rule_version`, `indicator`, timestamp | La alerta se actualiza y conserva su `alert_id`; así pasa a resuelta. |

Los timestamps deben ser UTC y terminar en `Z`, con segundos y fracciones
opcionales de cualquier longitud, conservadas sin redondear. Formas equivalentes como `12:00:00Z` y `12:00:00.000Z` son
la misma clave. Un valor ausente se guarda como `NULL` y se lee como `null`;
nunca se sustituye por `0` ni por un valor anterior.

### Validez de esquema no es normalidad clínica

La validación comprueba solo la forma: tipos, unidades, escalas (por ejemplo
SpO2 0-100, ánimo 1-5, sueño 0-24 horas), campos requeridos, que el día de
misión coincida con el timestamp y que el astronauta y la fuente existan. Una
frecuencia cardíaca de 250 se guarda como cualquier otro valor. Decidir si un
valor merece atención corresponde a los issues de análisis y alertas (#14, #15).

### Cómo se une el diario al summary (#8)

Las entradas de diario y las lecturas vitales son tablas separadas con cadencia
distinta. En `latest_metrics`, `sleep_hours_last_night` y `mood_score` vienen
del diario, y las tres métricas vitales de las lecturas. Cada métrica se elige
de forma independiente como su último valor no nulo y conserva su propio
timestamp, día de misión, procedencia e ID de registro. Las historias crudas
conservan sus null y huecos.

### API REST y demo

Endpoints disponibles: `GET /api/health`, `GET /api/astronauts`,
`GET/POST /api/astronauts/{id}/readings`, `GET/POST .../journal`,
`GET .../summary` y `GET .../alerts`. Los GET devuelven 200; los POST devuelven
201 al crear, 200 al reenviar una lectura idéntica o corregir/reenviar un diario.
Una lectura con la misma clave y valores distintos devuelve 409 sin sobrescribir.
Los IDs los genera el backend; los reintentos y las referencias conservan esa identidad.

Listas: `limit` entero 1–1000 (100 por defecto), `offset` >=0 (0 por defecto).
Historias/alertas: `from_day` y `to_day` inclusivos dentro de la misión, sin
inversión. Historias, summary y alertas aceptan `as_of` UTC terminado en Z,
dentro de la misión. Ausente: último timestamp persistido de lectura o diario
del perfil; null si no hay observaciones. Nunca se incluyen registros futuros.
Cada snapshot mantiene su fecha original. Perfiles se ordenan por ID; lecturas
y diario por timestamp e ID ascendente. Alertas aceptan `status=active|resolved`.
Los totales se calculan después de filtrar y antes de paginar.

Éxitos: `data/meta`. Errores: `error/meta`, con `code`, `message` y
`details[{field,message}]`. Códigos: 404 `ASTRONAUT_NOT_FOUND` solo para perfiles
inexistentes; 404 `NOT_FOUND` para rutas inexistentes; 405 `METHOD_NOT_ALLOWED`;
409 `READING_CONFLICT`; 422 `VALIDATION_ERROR` con campos `body.*`/`query.*`;
500 `INTERNAL_ERROR` genérico, sin trazas. Health y perfiles usan `as_of=null`.
Los POST usan el corte efectivo de la última observación, compatible con
`matchesView` del cliente. Un error nunca se convierte en historia vacía.

Hasta #14, los baselines usan `not_implemented`, valor/contexto/método/ventanas
null y cero muestras. Hasta #15, las alertas usan `not_implemented`, colección
vacía y total cero; el summary mantiene conteo/severidad null y alertas recientes
vacías. Eso expresa evaluación pendiente, no ausencia comprobada de alertas.

## Local ingestion and staged demo (#9) — English

Run all backend commands from `backend`, using `..\.venv\Scripts\python.exe`.
There is no upload endpoint, global simulation clock, scheduler, generated
mission, or new replay route. This workflow inserts only the requested days;
existing API `as_of` provides historical views after advancing.

```powershell
$env:ASTROHEALTH_DB_PATH = Join-Path $env:TEMP ("astrohealth-ingest-" + [guid]::NewGuid().ToString('N') + ".db")
..\.venv\Scripts\python.exe -m app.database init
..\.venv\Scripts\python.exe -m app.database import-json ..\docs\examples\mission_seed.json --until-day 3
..\.venv\Scripts\python.exe -m uvicorn app.main:app --port 8001
```

In another PowerShell from `backend`, set `ASTROHEALTH_DB_PATH` to the SAME
absolute path printed by the previous command, then advance and repeat:

```powershell
..\.venv\Scripts\python.exe -m app.database import-json ..\docs\examples\mission_seed.json --until-day 5
..\.venv\Scripts\python.exe -m app.database import-json ..\docs\examples\mission_seed.json --until-day 5
Invoke-WebRequest 'http://127.0.0.1:8001/api/astronauts/AST-001/summary' -UseBasicParsing
Invoke-WebRequest 'http://127.0.0.1:8001/api/astronauts/AST-001/readings?as_of=2026-11-03T23:59:59.999999999Z' -UseBasicParsing
```

Without `--until-day`, import the entire input. Day bounds are inclusive by
validated mission_day (UTC date), so all fractions of the last day's seconds
are included; the next day is excluded. All input records, including future
ones, are validated against existing data before the selection is committed.
A smaller requested day NEVER deletes later observations. The report lists
`profiles_with_later_data`, warns about the later records and gives actual
persisted cutoffs. Use `as_of` to query history. For a fresh staged run, use a
NEW path + `init`; `reset` is an offline, explicit operation that loads the
FULL seven-day seed, not an empty replay preparation. Preserve its existing
ownership/link/sidecar protections and close all database clients first.

CSV alternative (paths below are resolved relative to the manifest directory):

```powershell
..\.venv\Scripts\python.exe -m app.database import-csv ..\docs\examples\mission_seed.json --readings readings.csv --journal journal.csv --until-day 3
```

Minimal manifest: a JSON object containing exactly `schema_version`, `source`
(one SourceManifestEntry) and `astronauts` (array of Astronaut). A complete
mission_seed.json is also accepted as the CSV manifest: its `readings` and
`journal` members are ignored and replaced exclusively by the two CSV inputs.
Unknown other manifest fields are rejected. The manifest path itself is
relative to the current directory; CSV paths are relative to its directory
(or absolute). JSON bundle keys are exactly schema_version/source/astronauts/
readings/journal. Metadata maps through SourceManifestEntry -> sources and
Astronaut -> astronauts. Observations map through HealthReadingInput -> readings
and HealthJournalInput -> journal after extracting astronaut_id. Server IDs
are assigned by the existing repository; inputs do not supply record IDs.

CSV is UTF-8 (BOM accepted), with the exact header names from shared examples
in any order. Missing/duplicate/extra headers and short/long rows are errors.
Empty cells become null only in nullable fields. Zero is a value; numeric
`null`, `NaN`, `N/A`, infinity, boolean text and invalid integers are rejected.
Notes remain text; no medical units/context are inferred or converted.

Identical readings/journals and metadata are no-ops with stable IDs. Different
reading values/provenance, profiles or source manifests cause conflict. A
changed stored journal also conflicts by default, preserving API corrections.
Use `--update-journal` ONLY for deliberate journal replacement (stable ID).
Conflicting duplicates within an input still fail, even with that option.
This does not change HTTP journal upsert or the existing seed command.

Import is atomic for the entire bundle, including BOTH CSV files and metadata.
A transaction plus a rolled-back validation savepoint checks the whole input,
then publishes selected days under the same write lock. No executescript or
commit runs inside that import transaction. Invalid input/conflicts preserve
all previous rows. Error exit code is nonzero and no created rows are claimed.
Reports are JSON: effective paths, format/version, requested/selected days,
per-table created/repeated/updated counts, rejected bundle on failure, and
file/CSV line or JSON index/field diagnostics. The first storage conflict stops
the attempt; model validation can report several fields together.

Only synthetic provenance is accepted; terrestrial_biomedical belongs to the
separate DATA-03 workflow. Schema validity is not clinical normality.
After COMMIT, `post_import.cutoffs` supplies per-profile observation cutoffs
inside the requested replay day, ready to pass as API `as_of` for future #14/#15
reevaluation. `post_import.latest_stored_cutoffs` separately identifies the latest
observations physically stored. When replaying day 3 after day 5, the former
excludes days 4–5; the latter still reports day 5. No rows are deleted, and an
unfiltered API request still sees the latest stored data. An empty profile has
a null cutoff. No callback or engine is run; evaluation_status remains
not_implemented. No fabricated alerts or baseline changes are introduced.

Implementation checked with seven-day CORE-01 fixtures. Final validation with
Ismael's DATA-04 dataset is pending; these files are not DATA-04. The #8 pending
baseline rest/null discrepancy remains separate and unchanged by this issue.

Manifiesto mínimo: objeto JSON con `schema_version`, `source` (una fuente) y
`astronauts` (array de perfiles ficticios). Si usas el bundle completo como
manifiesto, se ignoran sus arrays de observaciones JSON: SOLO se leen los dos
CSV seleccionados. Se rechazan otras claves. La ruta del manifiesto es relativa
al directorio actual; los CSV son relativos a su directorio o rutas absolutas.
El bundle JSON completo exige además `readings` y `journal`, ambos arrays.

Mapeo: source -> SourceManifestEntry -> sources; astronauts -> Astronaut ->
astronauts; readings -> HealthReadingInput -> readings; journal ->
HealthJournalInput -> journal. Se extrae astronaut_id antes de validar los
Inputs; los IDs persistidos los genera el repositorio existente.

CSV UTF-8 con BOM opcional, cabeceras exactas de los ejemplos en cualquier
orden. Se rechazan cabeceras duplicadas/faltantes/desconocidas y filas con
columnas de más o menos. Vacío equivale a null solo en campos anulables; 0 se
conserva. No se convierten null/NaN/N/A/texto inválido en ausencia; tampoco se
suponen unidades o contextos médicos. Las notas siguen siendo texto.

La repetición idéntica es un no-op. Lecturas con la misma clave normalizada y
valores/procedencia distintos causan conflicto. Tampoco se sobrescriben perfiles
ni fuentes distintos. Un diario distinto del guardado causa conflicto por
defecto para proteger correcciones de la API. `--update-journal` permite una
corrección DELIBERADA conservando ID; duplicados contradictorios dentro del
archivo siguen siendo error. No cambia el upsert HTTP ni la semilla existente.

Se valida el bundle COMPLETO, incluidos registros posteriores al día pedido.
La validación completa usa un savepoint revertido; después se publica solo la
selección dentro de la misma transacción. Un fallo revierte toda escritura de
ese intento, incluidos metadatos y ambos CSV. No hay commits/executescript
internos que rompan la atomicidad. El informe JSON identifica entrada/destino,
formato/versión, días pedidos/seleccionados, creados/repetidos/actualizados por
tabla y errores con archivo/fila CSV o índice/campo JSON. Rechazo devuelve
código distinto de cero sin atribuir creaciones que terminaron en rollback.

El límite por día usa mission_day validado mediante fechas UTC: incluye TODAS
las fracciones del último segundo del día y excluye el siguiente. Retroceder
no borra nada: el informe advierte si ya hay observaciones posteriores.
`post_import.cutoffs` limita la vista al día pedido; pasa ese valor como `as_of`
a la API. `post_import.latest_stored_cutoffs` informa por separado del último
dato almacenado. Una consulta sin `as_of` sigue mostrando el último día real
de la base. Los perfiles vacíos conservan cutoff null.
Para una demo limpia usa una ruta nueva + init; reset requiere todos los
clientes detenidos y carga la semilla COMPLETA de siete días. No es un inicio
vacío de replay. Se conservan sus protecciones de identidad, enlaces y auxiliares.
